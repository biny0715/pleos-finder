## 2. 새로 합의한 핵심 기능: 스마트 멀티 픽업(Smart Multi-Pickup)

### 사용자 가치
운전자가 가족·친구 **여러 명을 순서대로 선택**하고 **최종 목적지**를 설정한다. **사용자가 선택한 순서를 기본 경로로 유지**하며, Finder가 실제 도로 기준으로 더 효율적인 픽업 순서를 계산했을 때만 **선택적 추천**을 제시한다. 사용자가 수락하면 추천 순서를 적용하고, 거절하거나 응답하지 않으면 **원래 사용자가 선택한 순서**로 현대차 기본 내비 경유지 안내를 진행한다. 특정 인원을 반드시 먼저 픽업하도록 고정할 수도 있다.

### 대표 시나리오
1. 운전자가 Finder의 가족·친구 목록에서 2명 이상 **원하는 픽업 순서대로** 선택한다(예: 엄마 → 아들 → 딸). 필요하면 '엄마 먼저 픽업'처럼 **순서 고정**을 설정한다.
2. 최종 목적지(예: 집)를 설정한다. **최적화 기능은 선택 사항**이며, 기본 경로는 사용자가 선택한 순서다.
3. 각 상대의 위치 공유 권한/현재 위치 유효성을 확인한다. '일시적 허용'인 경우 각 상대의 동의를 받으며, 미승인·거절·만료 상태를 표시한다.
4. 유효한 픽업 대상에 대해 실제 도로망/주행 시간으로 **지점 간 이동시간 행렬**을 획득한다.
5. 사용자가 고정한 픽업 순서를 절대 변경하지 않는 제약을 적용해, 차량 현재 위치 → 선택된 인원 → 최종 목적지의 더 빠른 **추천 순서**와 예상 절약시간을 계산한다. 추천을 계산할 수 없거나 이점이 없으면 기본 순서 그대로 진행한다.
6. 순서가 다르고 시간 단축 효과가 있으면 정차 시 간결한 확인 팝업과 가능한 경우 **Gleo AI 음성 안내**로 '현재 엄마 → 아들 → 딸 순서인데, 아들 → 엄마 → 딸 순서가 더 빠릅니다. 변경하시겠어요?'처럼 제안한다. **'추천 순서로 변경' / '기존 순서 유지'** 중 명시적으로 선택할 수 있어야 한다. 고정 대상이 있다면 그 제약을 위반하는 순서는 제시하지 않는다.
7. **수락 시에만** 추천 순서를 적용한다. 거절·무응답·음성 인식 실패 시 원래 순서를 그대로 유지한다. 음성 안내 또는 음성 수락/거절은 Gleo 공개 기능/지원 범위를 검증한 뒤 구현하며, 주행 중에는 플랫폼 UX 제한에 맞춰 시각 팝업과 상호작용을 최소화한다.
8. 확정된 순서로 NaviHelper 경유지 안내를 시작한다. 각 픽업 대상의 폰에는 **본인 차례까지 남은 예상 시간(분), 경로상 남은 거리(km), 예상 도착 시각, 픽업 진행 상태**를 표시한다. 앞선 픽업 인원을 거치는 경로 기준으로 계산하며 직선거리로 표시하면 안 된다.
9. 차량이 이동하거나 앞선 픽업이 완료되면 상대별 ETA/남은 거리를 갱신한다. 인원이 이동·취소·공유 종료되는 경우 남은 경로를 재계산하되 **운전자 승인 없는 자동 순서 변경은 하지 않는다**.
10. 마지막 픽업 뒤 최종 목적지까지 안내한다.

### 1차 범위(우선 구현)
- 기존 단일 픽업을 그대로 유지하는 **별도 멀티 픽업 모드**
- 다중 선택 UI, **선택 순서 유지**, 특정 대상 **우선 픽업/순서 고정**, 최종 목적지 설정, 위치 공유 동의 체크
- 이동시간 행렬 기반 **선택적 최적 순서 추천**, 고정 순서 제약 준수 및 예상 절약 시간 비교
- **추천 팝업 + 수락/거절**: 거절·무응답이면 기존 순서로 진행, 수락해야만 최적 순서 적용
- **Gleo AI 음성 추천 안내** 및 선택 응답은 SDK 지원 검증을 전제로 추가 설계
- 확정된 경유지 순서로 NaviHelper 안내 연계
- **각 대상별 본인 픽업까지 남은 분·km·예상 도착 시각**을 폰에 표시하고 진행 상황에 따라 갱신
- 픽업 완료/취소·위치 공유 만료 시 상태 갱신

### 후속/선택 범위 (1차 구현으로 단정 금지)
- 실시간 위치 이동에 따른 자동 재최적화 및 승인 UX
- 개인별 대기시간/탑승 후 차내 체류시간 등 다목적 최적화
- 다중 차량 배정, 시간 창(time window), 교통 예측 AI
- 안전하고 합법적인 승차 지점 추천(도로/출입구/정차 가능 데이터의 별도 확보·검증 필수)
- 차량 간 무전

### 음성·팝업 예시 (기획용, Gleo 지원 검증 전)

- 아빠가 **엄마 → 아들 → 딸** 순서로 선택하고 집을 최종 목적지로 설정한다.
- 순서 고정이 **없는** 경우, 주행시간 계산 결과 **아들 → 엄마 → 딸**이 더 효율적이면 Finder가 다음과 같이 추천한다.
  - 팝업: "현재 순서보다 **아들 → 엄마 → 딸** 순서가 약 8분 빠릅니다. 변경하시겠어요?" (8분은 실제 계산값으로 대체)
  - 버튼: **추천 순서로 변경 / 기존 순서 유지**
  - Gleo 음성 안내 목표: "아들을 먼저 픽업하면 약 8분 더 빠릅니다. 순서를 변경할까요?"
- **엄마를 반드시 먼저 픽업**하도록 고정했다면, 추천은 엄마를 첫 번째로 유지하는 범위 내에서만 탐색한다(예: 엄마 → 딸 → 아들). 고정 조건을 위반하는 아들 → 엄마 → 딸은 추천하면 안 된다.
- 수락하지 않으면 엄마 → 아들 → 딸을 그대로 안내한다. 이 거절은 오류가 아니라 정상 선택이다.
- 폰 앱의 아들/딸 화면은 **각자 본인이 픽업될 때까지** 남은 주행시간과 누적 거리, 예상 시각을 확인한다. 화면의 km는 그 사람까지의 **경로상** 거리이며 두 사람에게 항상 같은 ETA/거리를 보여주지 않는다.

## 3. 알고리즘 및 NVIDIA 기술에 대한 최종 결정

- **이번 단계는 (a) 현재 Finder 유지 + (b) 실제 도로 기반 멀티 픽업 경로 '선택적 추천'까지** 한다. 사용자가 정한 순서는 기본값이며, **추천은 강제 적용하지 않는다**.
- **Omniverse, Isaac Sim, Isaac Lab, 자체 학습 AI는 이번 기능의 필수 요소가 아니다.** 현재 기획서의 핵심 기술 스택에 학습 AI를 이미 사용한 것처럼 기재하지 않는다.
- NVIDIA **cuOpt는 선택적인 후속 최적화 엔진**이다. 특히 픽업 인원·차량 수·시간 제약이 늘어나는 경우 적용 검토한다. cuOpt 자체는 학습형 AI도, 내비게이션 도로 데이터 공급자도 아니다.
- 소수(예: 2~6명) 대상의 1차 프로토타입은 출발지·최종 목적지를 고정한 방문 순서의 **전수 탐색(n!)** 또는 간단한 최적화로 충분하다. 6명은 720개 순서다. 서비스 제한은 UX/지도 API 비용/성능을 보고 정한다.
- 단순한 직선거리로 최적화하면 안 된다. 최소한 실제 도로/일방통행을 반영한 **차량 이동시간**을 사용한다.
- 경로 데이터 공급자는 실제 이용 조건에 따라 검토: 기존 NaviHelper가 외부 앱에 임의 지점 간 경로 시간 행렬을 제공하는지 문서/API에서 확인한다. 제공하지 않으면 별도 라우팅 API/도로망 엔진(예: Google Routes, Valhalla/OSM 등)을 고려한다. 지도 서비스 약관·지역 커버리지·요금 검토 필요.
- **NaviHelper 경유지 기능은 정확한 v3.0.5 API 타입/호출 방식과 경유지 개수·갱신 제약을 SDK 코드/공식 문서로 확인한 뒤에만** 구체 코드로 기술한다. 앞선 대화의 예시 코드를 그대로 실제 코드라고 믿으면 안 된다.
- 추천 계산 목적: 우선 **차량 전체 예상 주행시간 최소화**, 단 **사용자가 지정한 픽업 우선순위/순서 고정**을 반드시 만족한다. **기본 경로는 사용자 선택 순서**이며 추천 적용 여부는 사용자가 선택한다. 개인별 대기 시간/탑승 후 체류시간을 목적함수에 반영하는 것은 후속 개선으로 분리한다.

## 4. 데이터·안전·예외 처리

- 권한 승인 이전에는 상대의 실제 위치를 최적화에 사용하지 않는다. 미승인 인원은 경로 포함 여부를 명시하고 동의를 기다린다.
- GPS가 오래됐거나 정확도가 낮은 경우 경고/대안; 위치 공유 취소 또는 타임아웃 처리.
- 한 명만 선택하면 기존 단일 픽업으로 자연스럽게 연결 가능.
- 픽업 경유지와 실제 도로에서 정차 가능한 장소는 다르다. 최초 버전은 상대 위치를 경유지로 사용하며, 승하차 안전 보장/최적 승차 지점 추천이라고 과장하지 않는다.
- 주행 중 복잡한 인원 선택·목적지 검색·순서 편집 등은 제한하고, 정차 중 구성하거나 Gleo 음성/간결한 승인 UX를 우선 검토한다.
- 길 안내 변경이나 재최적화는 **운전자의 명시적 수락 후에만** 적용한다. 거절·무응답은 원래 픽업 순서를 유지하는 정상 동작이다.
- Gleo 음성 제안은 실제 Gleo 지원 가능 여부 확인이 필요하다. 음성만으로 승인 처리가 불가능하면 정차 중 화면으로 선택하게 하며, 운전 중 방해되는 전체 화면 팝업은 지양한다.
- 각 탑승자에게 보여주는 **남은 km는 해당 사람을 픽업할 때까지의 실제 경로상 누적 거리**로 정의한다. 앞선 사람을 먼저 픽업한다면 해당 구간도 포함한다. ETA는 변경·지연 시 갱신하고 데이터 최신 시각을 표시한다.
- 서버에는 필요한 최신 위치와 진행 상태만 저장하며, 불필요한 이동 이력은 수집하지 않는다.
- API 실패, 네트워크 단절, 위치 공유 거절 시 기존 단일 픽업/수동 순서 선택 등 안전한 대안 UX 제시.
- 외부 지도 API 사용 시 개인정보 전달 범위, 서비스 약관, 쿼터·비용 확인.

## 5. 기획서 수정 방향 (Claude Code 실행 체크리스트)

- [ ] 서비스 소개를 '사람과 차량을 찾고 픽업 경로까지 최적화'로 확장하되 가족 케어 중심 포지셔닝 유지
- [ ] 메인 시나리오 A 단일 픽업 **유지**, 새 시나리오 '다중 픽업 후 최종 목적지' 추가
- [ ] 화면 구성에 멀티 선택·순서 고정·목적지·**추천 수락/거절 팝업**·진행 상태 UI 추가(구현 예정으로 표시)
- [ ] 사용자 선택 순서가 기본값임을 명시하고, 추천 거절·무응답 시 기존 순서 유지 처리 추가
- [ ] **Gleo AI가 최적 순서를 음성으로 제안**하는 시나리오 추가(실제 API 가능 여부 및 주행 중 제약 검증 필요)
- [ ] 폰 앱에 탑승자별 **본인 픽업까지 남은 시간(분)·거리(km)·ETA**와 경로 변경 시 갱신을 추가(구현 예정으로 표시)
- [ ] 주요 기능 표에 멀티 픽업 항목 추가하고 **계획 중** 명시
- [ ] 차량/폰/Firebase/라우팅 API/최적화 로직/NaviHelper 데이터 흐름 업데이트
- [ ] 예상 이동시간 행렬 → 제약조건 포함 순서 **추천** → 운전자 수락/거절 → 확정 경로 → 차량 내비 경유지 안내 아키텍처 설명
- [ ] 운전 중 UX, 공유 동의, 시간 만료, 픽업 상태별 예외 처리 정리
- [ ] 기존 기능 대비 차별성 서술: 단순 위치 공유가 아니라 동의 기반 단일/다중 픽업 + 목적지까지의 경로 최적화
- [ ] 개발 단계/마일스톤에 실제 구현 상태와 앞으로 구현할 단계 분리
- [ ] 최적화 엔진/지도 API/SDK 확정되지 않은 사항을 '검증 필요'로 표시
- [ ] 이미 존재하는 Gleo 함수 3개 상한과 충돌하는 새 명령을 임의로 확정하지 말 것. **음성으로 '변경하시겠어요?' 제안 및 수락/거절 응답**은 Gleo SDK에서 실제 가능한 방식인지 확인하고 불가하면 대안을 명시할 것
- [ ] 2026년 공모전의 제출 일정·요강이 변경됐을 수 있으니 공식 자료 재확인 없이 일정 확정 문구 추가 금지

## 6. 이름·브랜딩 결정

- **최종 유지: Pleos Finder (플레오스 Finder)**
- 이유: 'Find People(사람 찾기)', 'Find the Best Route(최적 픽업 경로 찾기)', 'Find Each Other(그룹에서 서로 찾기)'를 모두 포괄.
- 신규 후보 'Pleos Together'는 이번 방향에서 채택하지 않음.
- 제안 슬로건: **사람을 찾고, 최적의 길을 찾다.** 다만 사용자가 정한 경로를 존중하고 최적 경로를 **선택적으로 추천**한다는 가치를 함께 설명할 것.
- 공모전 설명 예시: '가족·친구의 위치를 동의 기반으로 공유하고, 여러 명을 픽업할 때 더 효율적인 순서를 **선택적으로 추천**하며, 사용자가 승인한 순서로 차량 내비게이션을 안내하고 탑승자별 남은 거리·시간을 알려주는 Pleos Connect 연동 서비스.'
- 상표·공식 서비스 명칭과의 충돌 여부는 별도 확인 필요.
